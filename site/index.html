HydraDB hackathon - Track 2, agent context layer

Your agent needs four tools.
It sees two.

Switchboard is a universal MCP gateway. It writes tool dependencies into HydraDB as a graph, returns an ordered plan for each task, and learns which route works from execution results. Any MCP client can use it.

More tools made the agent worse

Sixty MCP tools cost 5,453 tokens of schema on every turn. The model still has to guess which tool consumes the ID another tool produces. It learns the order by failing, and forgets it when the session ends.

BEFORE

Sixty schemas, no order

Four MCP servers. 60 tools. 5,453 tokens of descriptions and schemas. Order is a model guess, retried one call at a time.

AFTER

Two tools, one plan

One gateway. 169 tokens of schema. find returns a four-step plan from the graph. run executes it and updates the weights.

Index once. Plan in one traversal.

Tool order is a property of the data, not a prompt trick. The graph is the product, not a cache in front of one.

01 / INDEX

Discover and connect

switchboard index reads tools/list from every configured server, then writes tools, consumed and produced types, and a FEEDS edge wherever one output feeds another input.

02 / FIND

One graph query

The agent sends a task. BM25 picks a shortlist and a goal tool. One algo.MSpaths traversal returns ordered candidates. The plan passes a type check before it is returned.

03 / RUN

Execute and learn

The gateway runs the chain, fills each argument from an input or the previous step, and raises or lowers FEEDS.weight. The next plan starts from what worked.

The graph fixes order. The weights fix the route.

24 tasks, 18 train and 6 holdout, 3 replicates, 5 rounds. Each fixture family contains a trap tool with the same input and output types that fails at execution. A valid path is not automatically the right path.

What lives in HydraDB

(:Tool {id, key, name, server, consumes, produces, writes})
(:Tool)-[:FEEDS {weight}]->(:Tool)
(:Plan {id, key, task, hash, wins})
(:Plan)-[:STEP {i, args}]->(:Tool)

OSS HydraDB 0.4.0 with MinIO. One synchronous query per plan. Weights are read, rounded, and written back as data. No model call in the planner.

MCP SURFACE

Exactly two tools

find(task, inputs?) returns a plan id and numbered steps. run(plan_id, inputs?) returns one result per step or the failing step. The upstream catalog never enters the model's window.

Tested with OpenCode v2.2.5 as a real MCP client, over stdio and over the HTTP daemon with two concurrent clients.

Run it locally

docker compose up -d
pip install -e ".[dev]"
switchboard add mcp repo -- python -m tests.fixtures.repo_server
switchboard add mcp issue -- python -m tests.fixtures.issue_server
switchboard index
switchboard serve --http 127.0.0.1:8765

Point any MCP client at the stdio command or the HTTP endpoint. The four fixture servers and 60 tools are included so the numbers can be reproduced without external services.

SCOPE

What is real

Real: HydraDB graph, traversal, plans, weights, MCP transports, CLI, executor, OpenCode gateway run. Synthetic: the 60-tool catalog and its tasks. Not built: auth, tenancy, production hardening.

The live 60-native-tool model baseline is blocked by an OpenCode v2.2.5 tool-exposure issue. The 60-vs-2 token cost is measured from the real MCP tools/list payloads. Details in the repo.
